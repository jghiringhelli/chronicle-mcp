# RM-104 — Benchmark NFR-02/03/04 and write the numbers to `docs/evidence/`

**Load:**
- `docs/spec.md §5` — the NFR table; every row is *unrun*
- `docs/adrs/active/ADR-014-keyword-first-recall.md` §3 and its Verification section
- `docs/edrs/EDR-002-sqlite-memory-repository.md` — why NFR-03 is *at risk*, not merely unmeasured
- `src/adapters/repositories/sqlite-memory-repository.ts`
- **Do NOT load:** `sync.ts`, `coordination-service.ts`, any `[SPECIFIED]` feature section

**Scope:**

Three claims have been published since March and never measured. Measure them.

- **NFR-02** — cold start < 200ms: process spawn to the first `remember` returning, excluding
  package resolution.
- **NFR-03** — `recall` < 50ms with 10,000 memories stored. Seed a realistic store (mixed types,
  mixed projects, realistic content length), then measure recall at 1k / 10k / 50k so the shape
  of the curve is visible, not just one point. EDR-002 predicts O(rows): a leading-wildcard
  `LIKE` cannot use an index.
- **NFR-04** — the decay and promotion pass < 500ms at 50,000 memories.

Write a benchmark harness under `tests/bench/` (or `scripts/bench/`) that is **reproducible**: a
fixed seed, a stated machine, a stated Node version, and a JSON record per run under
`docs/evidence/`. A number with no recorded conditions is not evidence.

Then update `docs/spec.md §5`: each row becomes **verified (Nms on <machine>, <date>)** or
**missed (Nms, target Xms)**.

**A missed target is a successful outcome for this task.** If NFR-03 comes in over 50ms at 10k,
that is the finding, and it promotes RM-404 (FTS5) from conditional to scheduled. Do not tune the
benchmark until it passes.

**NOT IN SCOPE:**

- **Implementing FTS5.** That is RM-404, and it depends on this measurement. Measuring first is
  the point: optimising before measuring is how you end up with a fast path nobody needed.
- **Changing the recall query** in any way, including "obvious" improvements. The benchmark must
  measure what ships.
- **Relaxing a target** because the measurement missed it. Changing an NFR needs a `spec:` commit
  and an ADR, not a benchmark session.
- The other NFRs (01, 05, 06, 08, 09). Those are RM-105 / RM-302.

**Acceptance:**

- [ ] A benchmark harness runnable with one command, with a fixed seed
- [ ] Per-run JSON under `docs/evidence/` carrying: target, measured, machine, Node version,
      store size, timestamp
- [ ] NFR-02, NFR-03 and NFR-04 each measured, NFR-03 at 1k / 10k / 50k
- [ ] `docs/spec.md §5` rows updated to *verified* or *missed* with the number
- [ ] If NFR-03 is missed: RM-404 marked scheduled in `docs/roadmap.md`, and ADR-014's
      Verification section updated with the measurement
- [ ] `Status.md` gate table updated

**Commit:** `test(bench): measure NFR-02/03/04 and record the results`
